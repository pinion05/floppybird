# 💾 Floppybird

폴아웃(Fallout) 컨셉의 컨셉 전자기기 프로젝트. STM32가 구동하는 **MN12832L 128×32 VFD(진공 형광 표시관)** 디스플레이 위에 폴아웃 느낌의 메뉴 시스템과 미니 앱들을 올리는 것이 목표다.

```
floppybird/                          ← 이 저장소
├── run                              ← 실행 스크립트: ./run 한 줄로 미리보기 창 실행
├── AGENTS.md
├── mn12832l-stm32-driver/           ← VFD 드라이버: 하드웨어 추상화 + 호스트 스택 + 디지털 트윈
│   (Python 패키지 mn12832l-vfd, C 펌웨어 포함)
└── floppybird-app/                  ← 메뉴 애플리케이션: Fallout 컨셉 메뉴 + Tkinter 미리보기
    (Python 패키지 floppybird-app, mn12832l-vfd에 의존)
```

두 패키지는 같은 저장소 안에 있지만 별도로 설치된다 — 드라이버(`mn12832l-vfd`)가 하드웨어 계층, 앱(`floppybird-app`)이 드라이버 위의 애플리케이션 계층. `./run`이 두 패키지를 모두 editable 설치한 뒤 미리보기를 띄운다.

## ⚙️ "디지털 트윈"이지만 펌웨어는 실기용이다

이 프로젝트는 **디지털 트윈 기반으로 개발·검증**하지만, **C 펌웨어 코드 자체는 실제 STM32 하드웨어에 그대로 올라가는 운용 코드**다. 트윈이 "시뮬레이션 전용 코드"를 쓰는 게 아니다:

- **C 펌웨어** (`mn12832l-stm32-driver/firmware/stm32f0/`) — 실기 타겟 운용 코드. STM32F0 위에서 진짜 VFD를 구동한다: 43상 스캔, 240비트 핀 에미션, ISR 기반 latch, 안전 셧다운. 이 코드는 **트윈에서 검증한 뒤 손 하나 안 대고 실기에 플래시**한다.
- **Python 호스트 스택** (`mn12832l-stm32-driver/src/mn12832l/`) — 라즈베리파이가 그림을 렌더링해서 STM32로 보내는 역할. 나중에 `SubprocessTransport`로 실제 UART/USB 직렬을 통해 실기에 연결된다.
- **디지털 트윈** — C 펌웨어를 그대로 돌려 핀 신호를 가상으로 만들고, "이 코드가 실기에서도 똑같이 그려질 것"을 컴퓨터에서 검증하는 도구. 트윈이 시뮬레이션 전용 코드를 쓰는 게 아니라 **운용 펌웨어 자체를 돌려서 검증**하는 것이 핵심이다.

### 왜 이렇게 하는가

"컴퓨터에서는 됐다"가 "실기에서도 된다"를 보장하지 않기 때문이다. 트윈은 매 화면마다 `파이썬 → C 펌웨어 → 핀 시뮬레이션 → 재구성 → 원본과 일치하는가?` 라운드트립을 돌려서, 하나라도 틀리면 거짓 성공 화면 대신 빨간 에러를 띄운다. 이 검증을 통과한 화면은 실기에서도 똑같이 그려진다는 보증이 된다.

### 실기 전 남은 6단계 (하드웨어 검증)

소프트웨어는 끝났고, 하드웨어 검증이 남았다 (친구에게서 디스플레이를 받은 뒤):
1. 정확한 STM32F0 부품 ID 확인
2. 칩 회사 CMSIS/HAL 헤더 복원
3. 전원 용량·전압 측정
4. 오실로스코프로 신호 검증
5. 고압(HV) 듀티 사이클 점검
6. 실제 UART/USB 주변장치 선택·설정

## 🎛️ 하드웨어 입력 추상화 (모듈 교체 가능)

이 기기에는 물리 부품 5개가 달릴 예정이다. 소프트웨어는 이 입력을 **교체 가능한 부품(InputSource)**으로 추상화해서, "누가 버튼을 눌렀는지" 모르게 설계했다:

```
┌─ 메뉴 ──────────┐
│  입력 이벤트 받음 │  ← 누가 보냈는지 관심 없음
└────────┬────────┘
         │ 공통 약속 (버튼 번호 + 다이얼 움직임)
         ▲
         │ 이 부품만 교체하면 끝 (메뉴 코드는 한 줄도 안 고침)
         │
  ┌──────┴──────────────┐
  │  오늘: 컴퓨터 마우스 │  TkinterSource (미리보기 창의 가짜 버튼)
  │  나중: 진짜 물리 버튼 │  GpioSource (라즈베리파이 GPIO)
  └─────────────────────┘
```

- **로터리 엔코더** — 돌리기(화면마다 역할 다름: 메뉴 스크롤, 볼륨 등), 누르기(대부분의 화면에서 **선택/확인**)
- **버튼 4개** — `BTN1`~`BTN4`. `BTN4`=뒤로(확정), 나머지는 화면/모드마다 나중에 매핑

미리보기 창에서는 이 물리 부품을 마우스로 누르는 가짜 버튼으로 흉내 낸다. 나중에 같은 약속을 지키는 GPIO 입력 부품으로 교체하면 메뉴 수정 없이 실기 입력이 된다.

## 🚀 실행 (미리보기)

```sh
cd floppybird
./run
```

처음 한 번은 Homebrew로 Python 3.12 + Tk 8.6+(`python-tk@3.12`)를 확보하고, 가상환경을 만들고, C 디지털 트윈을 빌드한다. 그 뒤로는 바로 창이 뜬다.

> **참고 (Tk 8.5 버그):** macOS CommandLineTools Python(3.9)의 Tk 8.5는 캔버스를 화면에 렌더링하지 못하는 알려진 버그가 있다. `./run`이 Python 3.12와 `python-tk@3.12`(Tk 9.0)를 쓰도록 자동 설정하는 이유다.

창이 뜨면:
- 2초간 부팅 화면 → 자동으로 메인 메뉴로
- 다이얼 ◀/▶ 으로 메뉴 이동 (랩어라운드)
- 다이얼 누르기로 음악/게임/설정 진입
- `BTN4`로 메인 메뉴 복귀
- 아래 상태줄에 `DIGITAL TWIN: PASS`와 통계가 떠야 정상

## 🐛 트러블슈팅: 캔버스가 화면에 안 보일 때 (Tk 8.5 버그)

**증상:** `./run`으로 창은 뜨는데 VFD 캔버스가 하얗거나 비어 보인다. 버튼은 보이지만 메뉴 글자가 안 보인다.

**근본 원인:** Apple **CommandLineTools Python(3.9)이 번들한 Tk 8.5**에 macOS에서 캔버스를 화면에 렌더링하지 못하는 알려진 버그가 있다. 10년 넘게 미해결.

**진단 증거 (체계적 디버깅으로 확인):**
- 단순한 Tkinter Hello World도 같은 증상 → 우리 코드 버그가 아님
- Tkinter는 캔버스에 484개 사각형 객체를 정상 생성 (코드는 맞음)
- `screencapture -l`과 cua-driver 단일 창 캡처가 모두 실패/빈 이미지 → 백업 스토어 노출 안 됨
- Homebrew Python 3.11/3.12/3.14는 `tkinter` import 자체 불가 (`_tkinter` 빌드 안 됨)

**해결:** `./run`이 **Homebrew Python 3.12 + `python-tk@3.12`(Tk 9.0)** 를 자동으로 확보하도록 했다. `sudo` 불필요, bottle로 받아 5초면 끝. 이걸로 캔버스가 정상 렌더링된다.

**재발 방지:** `./run`은 venv가 Python 3.12 기반인지 검사하고, 구버전 Python 기반이면 자동으로 재생성한다.

## 📁 하위 패키지: `mn12832l-stm32-driver` (드라이버)

VFD 드라이버 + Python 호스트 스택 + 디지털 트윈. 세부 내용은 하위 `README.md`와 `ANALYSIS.md` 참고.

주요 구성:
- **Python 호스트 스택** — 프레임 렌더링, CRC 프레임 프로토콜, 전송/재시도, 직렬 브리지
- **STM32F0 펌웨어** (C) — 43상 스캔 드라이버, 호스트 링크 수신기, 핀 에미션, ISR, 안전 셧다운
- **디지털 트윈** — 핀 레벨 C 시스템 트윈 + Python TUI, 라운드트립 검증

## 📁 하위 패키지: `floppybird-app` (애플리케이션)

드라이버(`mn12832l-vfd`) 위에 올라가는 Fallout 컨셉 메뉴 시스템. 드라이버의 공개 API만 import한다.

- **VFD 메뉴 시스템** — 5화면 메뉴, 입력 부품 교체 가능(InputSource), Tkinter 미리보기
